# .memlog.md — commit_settlement RPC

Append-only. Each entry is one line. Never edit or reorder.

## Decisions

- 2026-09-04 — Replace three sequential Supabase network calls (balance UPDATE → statistics SELECT → statistics UPSERT) in `commitSettlement` with a single `commit_settlement` RPC. The three calls are not atomic: a failure between the UPDATE and the statistics write leaves balance and stats diverged. The RPC runs inside one implicit transaction; an unhandled exception rolls back everything.

- 2026-09-04 — RPC signature: `commit_settlement(_account_id uuid, _user_id uuid, _clamped_pnl numeric) RETURNS TABLE(new_balance numeric, clamped_pnl numeric)`. The parameter is `_clamped_pnl`, not `_raw_pnl`. The caller is responsible for clamping before invoking.

- 2026-09-04 — NOT FOUND raise after UPDATE. If the UPDATE matches zero rows, RAISE EXCEPTION with account_id and user_id in the message. A settlement that touched nothing must fail loudly (PAT-1 in SQL). The FOR UPDATE lock makes a zero-row match theoretically impossible between the locked SELECT and UPDATE, but defense-in-depth costs nothing.

- 2026-09-04 — Floor-bound violation raises EXCEPTION, not WARNING. RAISE WARNING writes to the PostgreSQL server log, which Supabase's postgREST interface does not surface to the JavaScript client. A branch that fires silently and corrects itself silently is unobservable — same shape as a discarded `{ error }`. Since the equivalence proof shows the floor-binding branch should never fire in correct callers, an exception is appropriate: it makes the contract self-enforcing during development and fails loudly in production.

- 2026-09-04 — Caller-side equity clamp: `effectivePnl = negative_balance_protection ? Math.max(pnl, -balance) : pnl`. The RPC also enforces `GREATEST(pnl, -locked_balance)` as defense-in-depth. The two clamps compose identically in every reachable case (see proof below). The RPC's clamped_pnl return value is the authoritative figure for statistics computation — it may differ from the caller's estimate if another settlement landed between the caller's balance read and the RPC's FOR UPDATE lock.

- 2026-09-04 — The RPC does NOT read open positions, equity, or floating PnL. Its contract is narrow: lock the account row, enforce the balance floor, write the new balance, return the authoritative state. Equity computation stays in TypeScript (`nextBalance`, `computeAccountRisk`).

- 2026-09-04 — GRANT EXECUTE to authenticated and service_role. Same pattern as the project's other SECURITY DEFINER functions.

- 2026-09-04 — BUG FOUND AND FIXED: RETURNS TABLE in plpgsql produces a SET OF rows; assigning to OUT variables alone emits zero rows. Without RETURN NEXT, every call returns [] while the balance UPDATE commits. Fix: added RETURN NEXT after the OUT assignments (lines 91). Caller must read result[0], not destructure directly. Array-shape contract recorded in caller-contract.md and migration header comment. Found before apply to database.

## Constraints

- Caller MUST apply the equity clamp before invoking this RPC. If a future caller passes an unclamped negative pnl when NBP is true, the floor silently becomes -balance instead of -equity. This changes settlement behaviour for accounts with open positions whose floating loss exceeds the cash balance. When NBP is false, both the caller and the RPC skip the floor — omitting the pre-clamp has no effect because neither layer clamps at all.

- Statistics computation (account_statistics.net_pnl, trade counts, win rates) is the caller's responsibility after the RPC returns. The RPC does not touch account_statistics.

- The RPC sets both balance and equity to the same value. Equity will be stale until the caller's next risk-snapshot computation, which is expected — equity reflects open-position state the RPC does not read.

## Proof — two-clamp equivalence

Today (single equity clamp in TypeScript):
```
caller: clampedPnl = clampRealizedPnl(rawPnl, acct) // cap at -balance
caller: balance = nextBalance(balance, clampedPnl) // max(0, balance + clampedPnl)
```
Because clamp guarantees `balance + clampedPnl >= 0` when NBP is on, `max(0, ...)` in nextBalance never binds. The equity clamp is effectively dead code when NBP is on and the input is already clamped.

After the change (caller equity clamp + RPC balance floor):
```
caller: effectivePnl = Math.max(pnl, -balance) // equity clamp
RPC: v_pnl = GREATEST(callerPnl, -lockedBalance) // balance floor
RPC: v_balance = lockedBalance + v_pnl
```

Case-by-case:

| raw pnl | balance | NBP | Caller out | RPC GREATEST | Final bal | Same? |
|---------|---------|-----|------------|--------------|-----------|-------|
| +500 | 1000 | on | 500 | 500 | 1500 | ✓ |
| -300 | 1000 | on | -300 | -300 | 700 | ✓ |
| -1500 | 1000 | on | 0 (clamped)| 0 | 0 | ✓ |
| -1500 | 1000 | off | -1500 | -1500 | -500 | ✓ |
| -200 | 0 | on | 0 | 0 | 0 | ✓ |
| -200 | 0 | off | -200 | 0 (floor) | 0 | ✓ |

The caller's `Math.max(pnl, -balance)` and the RPC's `GREATEST(pnl, -lockedBalance)` are algebraically equivalent constraints on the delta. Any pnl that passes the caller's check passes the RPC's. The only case where the RPC tightens further is when the caller read a stale balance (another settlement landed between the read and the FOR UPDATE lock) — the RPC's returned `clamped_pnl` is authoritative and must be used for statistics.

The "divergence case" (openPnL > 0 with loss beyond -balance) is unreachable because the equity clamp already caps at -balance before the RPC sees the pnl. No sequence of concurrent events can produce a pnl that passes the caller's clamp but fails the RPC's floor, because both clamps use the same mathematical constraint against the same quantity (balance as a floor for the loss).
